# 微信媒体读取与进程 Hook（2026-09-10）

当前部署使用本地消息库定位媒体，再读取已经落盘的文件。Frida 已接入 Docker 内当前微信主进程，观察媒体文件操作并保留文件；管理后台的媒体流程不再点击微信、打开聊天记录或上下滚动。

## 参考范围

参考 [Agent Console](https://github.com/zhx8702/agent-console) 的提交 `ed686d9910732e47eccc178d8cdba6cae818b7da`：

- `wxbot_client/sealed_core/ingest.py`：消息资源定位、图片解析，以及文件稍后落盘后的重试。
- `wxbot_client/image_decrypt.py`：V2 图片的 AES 前缀、明文中段、XOR 尾段布局。

该提交的上述入站查询只处理文字和图片；其中 Windows 内存读取代码不能当作 Linux 媒体函数 Hook 使用。项目中的应用层 Hook 也不等于注入微信进程。本次 Linux 文件操作 Hook 是 wxbot 的本地实现，没有照搬 Windows SDK，没有引入 Redis 或 PostgreSQL。

## 当前实现

`docker/frida_capture.js` 使用 Frida 观察微信进程的 `open/openat`、`close`、`rename`、`unlink` 等 libc 文件操作。在写入文件关闭、文件改名后或删除前，通过硬链接保留符合范围的媒体文件。只处理 `/root/xwechat_files/<账号>/` 下指定图片目录和 `msg/video`，捕获目录为 `/root/wxbot_capture/<账号>/`，保留账号目录的完整名称，不设跨账号共享池。

`docker/frida_capture_supervisor.py` 保证单个捕获进程运行，定期更新心跳；微信进程退出或连接断开后重试，发现多个同名微信进程时不任意选择。当前容器启动脚本已加入 Hook 启动块，使用 `/root/wxbot-hooks/current/`；Dockerfile 也包含 Frida 依赖和脚本，供后续重建。当前容器没有重启，完整重启链路尚未实测。

`core/local_media.py` 在当前账号目录保存媒体就绪状态，记录消息定位信息、状态和重试时间，不另存聊天正文。每次最多检查 4 项，同一项间隔至少 10 秒、最多尝试 90 次，队列最多 500 条。失败、预览图和封面可以等待文件到达后继续检查；超过次数后，用户可以点“更新媒体”重新检查。已经标记就绪的条目不周期性重查；图片实际读取接口仍会选择当前可读的较高分辨率版本。

- 图片：读取已有明文、捕获目录、归档及可解密的 `.dat`，经 Pillow 解码验证后选择较高分辨率候选。小图保守标记为预览；“已就绪”不等于已经证明是原图。
- 视频：查找原生文件目录和捕获目录中的 MP4，做基本 `ftyp` 头检查；封面与视频分别显示状态。这不是完整视频解码或文件完整性认证。
- 语音：沿用本地 VoiceInfo 数据库和 SILK 解码能力，不宣称文件 Hook 已覆盖语音数据库解密。

## 停用微信翻图

`core/harvest.py` 的旧入口已变为无界面操作的兼容空实现，`imgdec.schedule_fullres` 不再创建翻图任务。后台焦点循环已停用，归档中的全图导航关闭。

`POST /api/harvest`、`GET/POST /api/bot/fullres`、`POST /api/focus` 均不能再启用媒体导航；旧页面即使继续请求这些接口，也不会恢复翻图。新页面移除了自动解密/抓全图开关，以“更新媒体”和接收状态替代。网页自身的聊天滚动条仍用于浏览网页内容。

本改动只替换媒体读取路径。正常发送仍使用早期 `legacy_search` 发送脚本，发送时仍需搜索、粘贴和提交；没有改为 Hook 发送。此前的微信号优先搜索、单条结束语跳过、双方发言归属和重复回复检查继续保留。

## 验证结果与边界

- 16 个 Python 测试文件分别运行均通过；加上最终视频头检查案例，累计 376 项检查。媒体专项 15 项覆盖格式布局、重试、账号隔离、预览升级、封面状态及旧接口禁止导航。
- Python、Hook JavaScript、页面 JavaScript、启动脚本语法检查通过。
- 隔离进程和真实微信进程中的合成本地文件自检通过；最终 Hook 状态为 `ready`，微信 PID 保持 42。自检没有发送消息或操作窗口。
- 16 个现有本地图片文件对比：旧、新逻辑均有 7 个可读取，无样本回退；另外 9 个仍不被当前图片解码器支持，不能据此宣称解决全部微信图片格式。
- 已部署后台实际读取了 2 个已监听会话，6 条媒体消息均带状态字段；抽查的 3 张现有图片通过 HTTP 读取并成功解码。核查只输出计数，没有导出聊天正文或媒体内容。
- 后台实测机器人运行、增量读取就绪、发送方式为 `legacy_search`，Hook 在线，旧翻图入口返回 `ui_navigation=false`。早期发送脚本 SHA256 为 `0927c5c2b6f61db53734673b2186a3de8d312506178ca8f6352edb5408b2f624`，与切换前一致。

部署验证时真实新增媒体捕获计数为 0。本地自检证明 Hook 可以在目标进程内捕获合成文件，现有图片 HTTP 检查证明本地读取链路可用；两者不能替代一条真实新媒体消息从接收、捕获到展示的完整验证。

Hook 只保留微信已经写入本地、且由当前被注入进程通过已观察函数处理的文件。它不会主动下载未接收的原图或完整视频，不能保证捕获子进程、其他写入方式或所有临时目录中的媒体，也不能自动解决未知编码。同名目标已存在时保留原硬链接，不保证覆盖同名替换文件；硬链接要求来源与捕获目录位于同一文件系统。当前两者共用 `/root` 的绑定挂载，文件自检已经通过。捕获文件尚无自动清理策略。

本次未发测试聊天消息、未调用真实模型；未进行微信风控或账号长期稳定性验证，不能承诺 Hook 消除风控。
